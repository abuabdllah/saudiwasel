# تشغيل وصيانة SaudiWasel

## الهوية والروابط

بقيت المسارات القائمة كما هي، وأُضيف `/coverage` لتجميع طلبات مراجعة العنوان. الدومين المرجعي لجميع الصفحات هو `https://saudiwasel.com`، حتى في بيئة المعاينة. تضبط `lib/seo.js` بيانات الصفحات وOpen Graph وTwitter، ويظل `metadataBase` بالدومين الأساسي في تخطيطي العربية والإنجليزية.

لم تُعتبر صفحات الرياض والخبر الخاصة بالفايبر ترجمات مطابقة للأدلة الإنجليزية الخاصة بـ5G، ولا صفحة STC جدة ترجمة لدليل يقارن عدة مشغلين. بقي التبديل اللغوي بينها متاحًا، لكن hreflang اقتصر على الصفحات المتكافئة فعلًا واستخدم `ar-SA` و`en-SA` بروابط متبادلة. لكل صفحة canonical مستقل بلغتها.

## طلب التغطية والمتابعة

يبدأ الطلب بالمدينة والحي والمشغل المفضل والخدمة ونوع المبنى، ثم بيانات التواصل وموافقة حفظ الطلب. اقتراحات الأحياء ليست إعلانًا بتغطيتها. لا يوجد اتصال آلي بخرائط المشغلين، ولا يعطي الموقع نتيجة «مغطى» من مجرد إرسال البيانات.

يحفظ نموذج التغطية العربي الطلبات الجديدة في Netlify Forms باسم `coverage-request`. يحتوي `public/__forms.html` على نموذج HTML ثابت لجميع الحقول لاكتشافه عند النشر، وتُرسل البيانات إليه بترميز `application/x-www-form-urlencoded` مع `form-name`. فُعّل مؤشر Netlify Forms باستخدام سكربت التفعيل. بعد نشر النسخة، تُراجع الطلبات في Netlify Dashboard → Forms → coverage-request، بما في ذلك قسم Spam عند الحاجة. صفحة تعريف النموذج غير قابلة للفهرسة ولا تدخل sitemap.

بقي `/api/coverage-lead` وقاعدة Netlify Database وترحيل `20260930212432_create_coverage_leads` دون تعديل لحماية التكاملات والطلبات السابقة. لا يكتب النموذج الجديد نسخة ثانية تلقائيًا في قاعدة البيانات، ولا يوفر endpoint قراءة عامة للطلبات أو لبيانات العملاء. تستخدم الإدارة صلاحيات فريق الموقع للمراجعة؛ إتمام الاشتراك وتأكيد الخدمة والموعد النهائي يظل لدى المشغل.

احتُفظ بكل حقول النموذج وأُضيفت الملاحظات وموقع المبنى الاختياريان. يتحقق المتصفح من الحقول ورقم الجوال والموافقة، ويطبق Netlify Forms حماية الرسائل المزعجة وحقل `website` المخفي. ضوابط endpoint القديم لا تنطبق على Netlify Forms؛ صحة صيغة الرقم لا تثبت ملكيته، وتحتاج جودة الطلب ومعلومات المبنى إلى مراجعة بشرية.

يُجهّز مرجع مستقل بصيغة `SW-` مع 12 رمزًا عشوائيًا من أبجدية غير ملتبسة بواسطة `crypto.getRandomValues` (60 بت)، ويُحفظ مع الطلب؛ لا يُعرض إلا بعد نجاح POST. لا تُعرض UUID الداخلية. اختيار طول أكبر من ستة رموز يقلل احتمال التصادم، لكنه ليس ضمان تفرد رياضيًا أو قيدًا فريدًا في Netlify Forms. يحتفظ الطلب بنفس UUID والمرجع عند إعادة محاولة البيانات نفسها؛ قد يكرر Netlify Forms الطلب إذا انقطع الرد بعد الحفظ الفعلي، لذا يستخدم الفريق المعرف الداخلي لإزالة التكرار عند المراجعة.

بعد نجاح الحفظ فقط، تظهر رسالة التسجيل والمرجع وحالة انتظار مراجعة التغطية، ويحاول المتصفح فتح `wa.me/966564612017` برسالة تشمل الاسم والجوال والمدينة والحي والخدمة والمشغل والعقار والملاحظات والموقع عند إضافته. يبقى زر «إرسال الطلب عبر WhatsApp» ظاهرًا عند منع النوافذ التلقائية. فشل POST أو الشبكة لا يفتح واتساب ولا يعرض نجاحًا. لا تستخدم العملية API Token أو مفتاحًا في المتصفح. روابط التواصل العامة في الرأس والتذييل لا تمثل إرسال نموذج أو حفظ طلب. نموذج الاستفسار الإنجليزي يوضح أنه محادثة واتساب مباشرة، ولا يدعي حفظ الطلب أو نجاح Netlify Forms.

تُنفذ طلبات الاطلاع والتصحيح والحذف من خلال إدارة الموقع، بما يتوافق مع سياسة الخصوصية المنشورة. لا توجد مهمة حذف تلقائية أو لوحة إدارة عامة جديدة، ولا يُطلب رفع هوية أو رمز تحقق في فحص التغطية.

## الباقات والمصادر

احتُفظ بأسماء الباقات السابقة كمرجع تحريري فقط، وليست عروضًا مؤكدة اليوم. لم يُبقَ سعر أو سرعة أو ميزة مجانية غير متحقق منها كحقيقة حالية. تعرض الصفحات رابط المشغل الرسمي وتنبه إلى تأكيد الضريبة وتكلفة الجهاز والتركيب وشروط الالتزام.

توجد روابط المصادر في `lib/operator-sources.js`، و`verifiedAt: null` يعني أن تفاصيل عرض حالي لم تُراجع. لا تنشر قيمة متغيرة اعتمادًا على اسم باقة قديم أو لقطة شاشة. يتطلب نشر أسعار أو سرعات فعلية مصدرًا مباشرًا للعرض وتاريخ تحقق حقيقيًا وشروطه وآلية للمراجعة الدورية. تاريخ تعديل الصفحة في sitemap ليس تاريخ تحقق من أسعار المشغل.

## إطار صفحات الأحياء

لم تُنشر صفحات أحياء جديدة دون دليل طلب بحث وبيانات تحريرية كافية. الأحياء المذكورة في صفحات المدن والنموذج بقيت اقتراحات لفحص عنوان المبنى وليست صفحات آلية.

يدعم `lib/neighborhoods.js` سجلات تحريرية معتمدة فقط. يحتاج سجل النشر إلى `city` و`slug` و`name` و`description` و`introduction` و`addressAdvice` وثلاثة أسئلة وأجوبة مفيدة على الأقل، إضافة إلى `sources` و`editorialReviewDate` و`demandEvidence` وحالة `published`. يجب أن يكون المحتوى مخصصًا للعقار والحي، وأن توضح المصادر حدود المعلومات. لا تخزن معلومات عملاء أو تقارير بحث خاصة في هذه البيانات العامة.

يعترض الإطار على مدينة غير موجودة أو slug يتعارض مع مشغل أو مسار 5G أو سجل مكرر. بعد اعتماد حي، تُضاف صفحته إلى التوليد الثابت وsitemap وروابط المدينة وbreadcrumbs من السجل ذاته، دون إنشاء مئات الصفحات. يجب أن تشير روابط المشغلين في السجل إلى مسارات موجودة، وألا تتضمن ادعاء تغطية حي كامل.

## قياس التحويلات

أُتيحت الأحداث التالية في `window.dataLayer` وفي حدث المتصفح `saudiwasel:conversion` دون أي Tracking ID جديد: `click_phone` و`click_whatsapp` و`coverage_check_start` و`coverage_check_submit` و`lead_submit` و`lead_success` و`operator_click` و`city_click`. بقي `coverage_check_whatsapp` متاحًا عند النقر على زر إرسال الطلب المحفوظ إلى واتساب. لا تُحسب روابط الأحياء أو 5G المدينة كنقرات على مشغل.

لا تتضمن بيانات القياس الاسم أو الجوال أو الحي أو مرجع الطلب. يعني `lead_submit` و`lead_success` أن Netlify Forms أعاد استجابة نجاح للنموذج العربي؛ أما `coverage_check_submit` فيقيس محاولة إرسال الطلب وليس تأكيد التغطية. إضافة مستهلك خارجي للأحداث تتطلب معرفًا حقيقيًا وإعدادات خصوصية مناسبة؛ تهيئة الأحداث وحدها لا تنشئ تقارير Google Analytics.

## التحقق

يشغّل `npm run check:types` تدقيق TypeScript دون إنشاء ملفات، ويشغّل `npm run audit:seo -- http://localhost:8889` التدقيق على خادم التطوير. يمكن تشغيل الخادم المحلي بوساطة Netlify CLI باستخدام المنفذ 8889. تراجع الأداة sitemap وجميع صفحاته وcanonical والعناوين والوصف وH1 وOpen Graph وTwitter وhreflang وFAQ الظاهر وArticle وbreadcrumbs والروابط الداخلية والمرابط وصور المشاركة وrobots. تحفظ نتيجة الفحص في `.netlify/seo-audit.json`.

نجح تدقيق 71 صفحة واردة في sitemap دون أخطاء، ونجح `npm run check:types`. نجحت 12 حالة اختبار متصفح موزعة على Desktop Chromium ومحاكاة Android Pixel 7 ومحاكاة iPhone Safari/WebKit: نجاح POST وحالات الانتظار ومنع الإرسال المتكرر ورسالة النجاح وكامل محتوى واتساب والنقر الفعلي على زر fallback، رفض الرقم غير الصحيح وغياب الموافقة، فشل HTTP وفشل الشبكة وعدم فتح واتساب أو عرض نجاح فيهما، ثم إعادة المحاولة. كانت استجابات Netlify Forms محاكية؛ لم تُرسل بيانات اختبار إلى الإنتاج ولم يُثبت حفظ طلب فعلي في Dashboard. حُفظت التقارير في `.netlify/seo-audit.json` و`.netlify/coverage-browser-audit.json`. محاكاة الأجهزة ليست اختبارًا على أجهزة فعلية، ولا تثبت توفر التغطية أو جودة الشبكة.

يتطلب التحقق النهائي بعد النشر مراجعة ظهور `coverage-request` في Dashboard، وإرسال طلب بإذن صاحب بياناته، ومطابقة مرجعه وحقوله، وفحص Spam عند غياب الطلب. رسالة نجاح HTTP في اختبار محاكى ليست إثباتًا لاستلام Netlify Forms في الإنتاج.

لم يُشغّل أمر بناء محلي في هذه الجلسة لأن بيئة التنفيذ أوكلت فحص البناء إلى المنصة تلقائيًا. فحص التطوير لجميع المسارات وتدقيق الأنواع لا يحلان محل نتيجة البناء الإنتاجي أو اختبار الخدمة بعد النشر، ولا يمثلان قياسًا فعليًا لـCore Web Vitals.
